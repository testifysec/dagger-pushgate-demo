# How we push: testifysec/dagger-pushgate-demo

Pushes to this repository go through pushgate.dev, a gate that verifies each push
before it reaches https://github.com/testifysec/dagger-pushgate-demo.git. Generated by the pushgate.dev setup document; if this
page and the policy page below disagree, the policy page is current.

## Remotes

`origin` fetches from https://github.com/testifysec/dagger-pushgate-demo.git and pushes through https://pushgate.dev/gh/testifysec/dagger-pushgate-demo.git.
The push URL in `.git/config` carries this clone's push credential, which is
never written here. Read the remotes back without printing it:

    git remote -v | sed -E 's#://[^@/]+@#://REDACTED@#'

Remote and signing settings live in `.git/config` and are set once per clone
on the host, outside any sandbox: https://pushgate.dev/docs/agent-sandbox#residual-gaps

## Policy

- **Signed pushes**: Every push is signed by a known identity.
- **Git metadata**: Record the commit and repository for every push.
- **Agent metadata**: Record what the tool could observe about its agent context.

No additional code checks are configured.

Policy page: https://pushgate.dev/gates/push/github.com%2Ftestifysec%2Fdagger-pushgate-demo?onboarding=1

## Signing

cilock is the only signer: commits and tags are signed by cilock (commit.gpgsign, tag.gpgsign) and every push carries a cilock push certificate (push.gpgsign).

## Agent identity

Each agent signs as its own enrolled identity, never a human login. Your human
approves enrollment in the platform browser with a passkey:

    cilock enroll agent --repo 'testifysec/dagger-pushgate-demo'

Check the principal, repository scope and expiry before a session:

    cilock agent status

The identity is time-bound: eight hours by default, seven days at most, with no
extension. Renewal requires a new human-approved ceremony.

## Before every push

    cilock attest --step push-metadata -a git -a alps-evidence

Your loop is: make changes, commit, record metadata, push.

## When a push is refused

A refusal arrives on stderr as prose for a human and as JSON on a line
containing `pushgate-challenge: `. Parse that line rather than the prose above it — the prose is written for a
human and may be reworded, the JSON is a contract. It carries:

- `commit` — the commit you must produce evidence FOR. Attesting a different
  commit is the most common way an honest retry still fails.
- `missing_evidence[]`: one entry per failure that refused the push. Do
  EVERY entry before you push again, not only the first. Most carry a
  `command` that produces exactly what is missing. A policy release gets one
  entry per commit it refused, naming its `release`, the `commit` and the
  `refs` that carry it; two releases that refuse the same push are two
  entries, and the same step name under two releases is two commands to run.
  A release entry lists one command per failed step in `commands[]`; each is
  a `cilock run` or `cilock attest --step` line. A `command` of `null` is
  not a pass. Check `type` before you act. On `release-owner-action` no
  command can fix it: stop and give your human the `owner_action` sentence.
  On `release` this gate could not turn the signed verdict into a command:
  show your human the refusal.
- `complete`: `true` when `missing_evidence` lists every failure that
  refused the push. When it is `false`, `missing_evidence_omitted` more were
  left out for size: do the listed work, expect the next push to name the
  rest, and tell your human. Absent on an older gate, whose list may name one
  release of several.
- `warnings[]`: failures in warn mode. They did not refuse the push and
  nothing in them is required.
- `evaluated` — whether a policy evaluation actually happened. When it is
  `false` the platform never answered, so NOTHING about your evidence was
  judged: the evidence you already have is still good. Do not re-run the gate
  and do not amend the commit; both throw away work that was never the problem.
- `retry_without_changes` — whether pushing the identical bytes again could
  ever succeed. It is `true` for a stale nonce, and for a
  `platform-unavailable` entry (a timeout or outage). When it is `false`,
  pushing again without doing the work returns the identical answer, so do not
  spend attempts on it.
- `policies[]` — the real policy documents this push was judged against, if
  you want the whole contract rather than the remedy. `readable_by` says who
  can open each `url`: `anyone`, or `signed-in human` for a signed release.

If the same rejection repeats after you followed its remedy, stop and show your
human the full message rather than retrying.

## Decisions that belong to a human

- Policy: activating or changing a policy is approved by a human at the policy
  page above. An agent may prepare and explain a draft.
- Agent identity: enrollment and renewal need a human's passkey approval.
